# Сборка

Запускайте сборку из корня репозитория. DMK поддерживает сборку для всех линеек HHKB: Classic, Classic Type-S, Hybrid и Hybrid Type-S (как ANSI 60 клавиш, так и японских JIS 69 клавиш).

## Версия компилятора

HHKB в CI собирается **Arm GNU Toolchain 15.3.Rel2 (GCC 15.3.1)** из [официального релиза Arm](https://gitlab.arm.com/tooling/gnu-toolchains-for-arm/-/blob/releases/15.3.rel2/README.md) с фиксированной проверкой SHA256. Для локальной сборки используйте ту же версию и поставьте её каталог `bin` первым в `PATH`. Проверьте `arm-none-eabi-gcc --version`; после смены компилятора пересоберите с `-c`. Для HHKB сохраняется обычная сборка `-Os` без LTO. Старые версии компилятора могут превысить лимит Bank 2 Hybrid в 64 КиБ, даже если выбранная версия укладывается.

## Команды сборки

### 1. HHKB Classic и Classic Type-S (Wired)

```bash
# Classic (ANSI 60 кл.):
./build_all.sh -b hhkb -d HHKB_CLASSIC

# Classic Type-S (ANSI 60 кл.):
./build_all.sh -b hhkb -d HHKB_CLASSIC_TYPE_S

# Classic Type-S JIS (69 кл.):
./build_all.sh -b hhkb -d HHKB_CLASSIC_TYPE_S,HHKB_JIS
```

PowerShell (Windows):

```powershell
.\build_all.ps1 -Keyboard hhkb -Define HHKB_CLASSIC
.\build_all.ps1 -Keyboard hhkb -Define HHKB_CLASSIC_TYPE_S
.\build_all.ps1 -Keyboard hhkb -Define HHKB_CLASSIC_TYPE_S,HHKB_JIS
```

### 2. HHKB Hybrid и Hybrid Type-S (Bluetooth + USB)

Для Hybrid собирается сырой бинарный образ STM32 с поддержкой SPI-протокола обмена с чипом Nordic nRF52832:

```bash
# Hybrid / Hybrid Type-S (ANSI 60 кл.):
./build_all.sh -b hhkb -d HHKB_HYBRID -c

# Hybrid / Hybrid Type-S JIS (69 кл.):
./build_all.sh -b hhkb -d HHKB_HYBRID,HHKB_JIS -c
```

После сборки бинарник упаковывается в финальный контейнер поверх оригинальной прошивки PFU скриптом `tools/hhkb/patch_hybrid_hfb.py` (подробнее ниже в разделе [Патчинг заводского образа Hybrid](#только-hybrid-локальная-сборка-и-патчинг-заводского-образа)).

STM32L072 выбирается через `DEFAULT_MCU` в конфигурации клавиатуры, поэтому в команде сборки не нужен аргумент MCU. В каталоге результата создаются контейнер `.hfb` для PFU и сырой `.bin` для Bank 2; сборка не прошивает клавиатуру.

### Результат сборки Hybrid и следующий шаг

Команды выше компилируют только открытый образ STM32: `build/hhkb-script/dmk_hhkb_stm32l072.bin`. Для ANSI/Type-S используйте `HHKB_HYBRID`, для JIS/Type-S JIS — `HHKB_HYBRID,HHKB_JIS`. Отдельного флага Type-S для Hybrid нет. Собирайте варианты по очереди: выходной каталог общий.

Можно не компилировать самостоятельно: [GitHub Actions](#github-actions) публикует `dmk-hhkb-hybrid-ansi-stm32` и `dmk-hhkb-hybrid-jis-stm32` с соответствующими `.bin`, HTML-патчером и `via.json`. Готовые пропатченные Hybrid HFB не распространяются, поскольку включают закрытый код Nordic.

После получения BIN самостоятельно скачайте подходящую оригинальную прошивку PFU и создайте HFB через [HTML-патчер и инструкцию установки](install.md#hybrid-local-patching). Эта локальная упаковка обязательна даже для BIN из CI. Для варианта с Python см. раздел ниже. Сама сборка или упаковка не записывает клавиатуру.

## Генерация раскладок VIA и Vial

`keyboards/hhkb/via.json` — единый источник физической геометрии ANSI и JIS:
ширины клавиш, отступов и формы JIS Enter. Изменяйте геометрию в этом файле,
сохраняя соответствие координат матрицы с `config.h`.

При сборке HHKB скрипт `tools/hhkb/generate_vial.py` создаёт компактный `vial.json`
в каталоге сборки, после чего он сжимается в `vial_generated.h`. Геометрия
сохраняется полностью; меню VIA и пользовательские коды клавиш исключаются,
как и раньше. Изменение исходного JSON автоматически обновляет оба результата.
Общий скрипт `tools/vial/generate_json.py` создаёт только сетку матрицы из
`config.h` и не используется для физической раскладки HHKB.

Чтобы обновить компактный файл в репозитории без сборки и прошивки клавиатуры:

```bash
python3 tools/hhkb/generate_vial.py keyboards/hhkb/via.json keyboards/hhkb/vial.json
```

### Структура, разметка и версионирование контейнера HFB

Официальные файлы обновления прошивок PFU и образы DMK используют специализированный формат контейнера `.hfb`.

#### Classic / Classic Type-S (ANSI/JIS)

**Размер контейнера:** 65 570 байт.

**Структура:**

```text
Внешний CRC-16/MCRF4XX (2 байта)
Внутренний CRC-16/MCRF4XX STM32 (2 байта)
STM32 Bank 2, дополненный 0xFF (65 536 байт)
Постфикс: 14 x 0xFF, модель (6), версия (4), 6 x 0xFF
```

**Побайтовая разметка:**

- `0x0000–0x0001`: внешний CRC по `[0x0002:]`.
- `0x0002–0x0003`: внутренний CRC по STM32 `[0x0004:0x10004]`.
- `0x0004–0x10003`: образ STM32 размером 64 КиБ, слинкованный по `0x08010000` и дополненный `0xFF`.
- `0x10004–0x10011`: 14 байтов заполнения `0xFF`.
- `0x10012–0x10017`: ASCII ID модели: `AHHX01`, `AHHS01` или `AHKS01`.
- `0x10018–0x1001B`: байты версии.
- `0x1001C–0x10021`: шесть завершающих байтов `0xFF`.

**Контрольные суммы:** обе CRC используют отражённый полином `0x8408`, начальное значение `0xFFFF` и отсутствие завершающего XOR. Внутренний CRC зависит от образа STM32 и не является фиксированным тегом модели.

**Версионирование:** результат DMK — `A4.50` (`AHHX01`), `A8.50` (`AHHS01`) или `A9.50` (`AHKS01`). Например, `A4.50` кодируется как `0A 04 05 00`.

**Упаковка:** `make_hfb.py` создаёт готовый контейнер из бинарника STM32 DMK и вычисляет обе CRC. Оригинальная прошивка и патчинг не нужны.

#### Hybrid / Hybrid Type-S (ANSI/JIS)

**Размер контейнера:** 282 672 байт.

**Структура:**

```text
Внешний CRC-16/MCRF4XX (2 байта)
Внутренний CRC-16/MCRF4XX STM32 (2 байта)
STM32 Bank 2, дополненный 0xFF (65 536 байт)
Данные обновления и прошивка Nordic (сохраняются)
ID модели (6), версия (4), хвост 0xFF (6)
```

**Побайтовая разметка:**

- `0x0000–0x0001`: внешний CRC по `[0x0002:]`.
- `0x0002–0x0003`: внутренний CRC по STM32 `[0x0004:0x10004]`.
- `0x0004–0x10003`: образ STM32 размером 64 КиБ, слинкованный по `0x08010000` и дополненный `0xFF`.
- `0x10004–0x4501F`: данные обновления и прошивка Nordic, сохраняемые без изменений.
- `0x45020–0x45025`: ASCII ID модели: `AHUX01` (ANSI) или `AHJX01` (JIS); `[-16:-10]`.
- `0x45026–0x45029`: байты версии; `[-10:-6]`.
- `0x4502A–0x4502F`: шесть завершающих байтов `0xFF`.

**Контрольные суммы:** обе CRC используют отражённый полином `0x8408`, начальное значение `0xFFFF` и отсутствие завершающего XOR. Внутренний CRC зависит от образа STM32 и не является фиксированным тегом модели.

**Версионирование:** результат DMK — `A0.50` (ANSI: `0A 00 05 00`) или `A2.50` (JIS: `0A 02 05 00`). Исходные заводские шаблоны остаются A0.48 и A2.49.

**Упаковка:** `hhkb.html` и `patch_hybrid_hfb.py` локально заменяют образ STM32, обновляют версию и обе CRC, сохраняя все данные обновления Nordic. Пропатченные контейнеры не распространяются, поскольку содержат закрытую прошивку.

> [!NOTE]
> PFU-совместимая версия в контейнере HFB (A4.50, A8.50, A9.50, A0.50, A2.50) нужна исключительно бутлодеру PFU для проверки файла обновления. Версия DMK CalVer/коммит внутри самого бинарника STM32 (отображаемая в интерфейсе VIA) независима от поля версии HFB.

## 3. Потребление памяти (Flash и RAM)

[Разметка линкера HHKB](../../../../platforms/stm32l072/stm32l072_bank2.ld) предоставляет **65 536 байт Flash Bank 2** по адресам `0x08010000–0x0801FFFF` и **20 480 байт SRAM**. Это сборки кода коммита `3e48c218` от 24 ноября 2026 года: **Arm GNU Toolchain 15.3.Rel2 / GCC 15.3.1**, `-Os`, без LTO, стандартная конфигурация со сжатым хранением EEPROM и восстановлением SW5+SW6. Все размеры указаны в байтах.

### HHKB Classic

| Вариант | Flash занято / 65 536 Б | Flash свободно | RAM выделено / 20 480 Б | RAM не выделено |
| --- | ---: | ---: | ---: | ---: |
| ANSI: Classic / Classic Type-S | 51 320 (78,31%) | 14 216 | 18 080 (88,28%) | 2 400 |
| JIS: Classic Type-S | 51 088 (77,95%) | 14 448 | 18 632 (90,98%) | 1 848 |

Разбивка выделенной RAM по секциям:

- **ANSI:** `.data` 2 536 + `.bss` 13 492 + `._user_heap_stack` 2 052 = **18 080**.
- **JIS:** `.data` 2 504 + `.bss` 14 080 + `._user_heap_stack` 2 048 = **18 632**.

Classic и Classic Type-S ANSI собраны отдельно; расход памяти у них одинаковый.

### HHKB Hybrid

Включены SPI-обмен с Nordic, телеметрия батареи и состояния сна/OFF. Type-S использует ту же сборку.

| Вариант | Flash занято / 65 536 Б | Flash свободно | RAM выделено / 20 480 Б | RAM не выделено |
| --- | ---: | ---: | ---: | ---: |
| ANSI: Hybrid / Type-S | 62 760 (95,76%) | 2 776 | 18 328 (89,49%) | 2 152 |
| JIS: Hybrid / Type-S | 62 560 (95,46%) | 2 976 | 18 888 (92,23%) | 1 592 |

Разбивка выделенной RAM по секциям:

- **ANSI:** `.data` 2 592 + `.bss` 13 688 + `._user_heap_stack` 2 048 = **18 328**.
- **JIS:** `.data` 2 560 + `.bss` 14 276 + `._user_heap_stack` 2 052 = **18 888**.

У Hybrid ANSI теперь остаётся **2 776 байт** Flash Bank 2, у JIS — **2 976 байт**. Компилятор, флаги функций и строки версии прошивки могут изменить эти значения.

### Оптимизация памяти и фоновой работы

LUT кривой EC строится целочисленной арифметикой Q20 при загрузке или изменении настроек. Таблица RAM размером 252 байта и целочисленная интерполяция при сканировании остаются прежними. Перестроение выполняется после возврата из загрузчика калибровки, чтобы их большие стековые кадры не вкладывались друг в друга в задаче матрицы.

HHKB использует статически созданную очередь матрицы. Удаление недостижимого создания динамической очереди позволяет линкеру исключить кучу FreeRTOS размером 2 КиБ из этих стандартных сборок. Vial также не резервирует в RAM HHKB неиспользуемые энкодеры и выравнивание до страницы Flash; формат компактной сериализации EEPROM не изменился.

Когда энергосбережение USB приостанавливает сканирование, прерывания таймера опроса отключаются и заново запускаются при возобновлении. В покое задача USB HHKB ждёт уведомления от USB и производителей данных, обслуживая фоновые проверки раз в секунду; незавершённая запись EEPROM сохраняет частое обслуживание. Отчёты клавиатуры будят задачу сразу. На остальных платформах прежняя частота фоновых проверок USB сохранена.

Сканер дополнительно кэширует точные пороги АЦП срабатывания/отпускания и последний сырой отсчёт: 376 байт для ANSI или 468 байт для JIS, плюс 4 байта версии диапазонов. В обычном режиме нормализация и LUT не нужны, если выключен EC Stream. В RT ход рассчитывается один раз на клавишу и используется также для логирования. Нормализация совмещается с межклавишной паузой стабилизации, обновление состояния — с преобразованием следующего отсчёта АЦП. Для сокращения работы на клавишу используются дополнительный кэш и код в RAM; таблицы выше учитывают этот расход.

С `HHKB_SCAN_DIAGNOSTICS=1` контрольные сборки занимают Flash/RAM соответственно: Classic ANSI **51 784 / 18 120 Б**, Classic JIS **51 560 / 18 672 Б**, Hybrid ANSI **63 256 / 18 368 Б**, Hybrid JIS **63 056 / 18 928 Б**. В диагностической сборке Hybrid JIS остаётся **1 552 Б** невыделенной RAM. Реальный запас стеков и соблюдение сроков сканирования нужно измерять на плате; см. [подробные тайминги сканирования](via-debug.md#подробные-тайминги-сканирования-ansi-и-jis).

### Как читать значения

Занятая Flash — длина сырого `.bin`, включая образ инициализации `.data` и функций в RAM. Размер дополненного HFB-контейнера не показывает объём занятой Flash. Выделенная RAM считается как `.data + .bss + ._user_heap_stack`: `.data` включает функции в RAM, `.bss` — статические стеки задач, а `._user_heap_stack` резервирует основной стек/стек прерываний с выравниванием. Динамическая куча FreeRTOS в этих стандартных сборках HHKB не включена; дополнительные модули с динамическим выделением памяти могут вернуть её в сборку. Невыделенная RAM не является измерением свободной кучи или запаса стеков во время работы.

```bash
arm-none-eabi-size -A -d build/hhkb-script/dmk_hhkb_stm32l072
arm-none-eabi-objdump -h build/hhkb-script/dmk_hhkb_stm32l072
```

### EEPROM

[Сжатое хранилище DMK](via-debug.md#сжатое-хранение-eeprom) резервирует **1772 байта** из 6144 байт EEPROM для всех поддерживаемых вариантов Classic/Hybrid ANSI/JIS: два снимка по 880 байт и 12 байт заголовка владения/сброса. Это отдельная память, она не включена в расход Flash и SRAM. Каждый снимок допускает 860 байт сжатых данных; фактическая длина зависит от сохранённой конфигурации. Остальная EEPROM содержит в том числе заводские данные PFU и не считается свободной областью DMK.

Откройте страницу локально, выберите официальный HFB и бинарник DMK, затем нажмите Patch and download. Заводская прошивка радио сохраняется. Шаг сборки HFB с пустым радио закомментирован.

[Workflow Build Firmware](../../../../.github/workflows/build_test.yml) запускается для `push` и `pull_request` в `main`/`master`; его можно запустить вручную через **Actions → Build Firmware → Run workflow**. После успешного запуска скачайте в разделе **Artifacts** нужный архив:

В каждом архиве лежат `.hfb` для выбранной модели и [via.json](../../via.json) для загрузки пользовательского меню через вкладку Design [веб-версии VIA](https://www.usevia.app/). Выбирайте архив по модели клавиатуры; сборка Type-S пока проверена компилятором, на плате проверялась обычная Classic.

## Почему необходим патчинг прошивки Hybrid

В отличие от HHKB Classic, где файл обновления содержит прошивку только для одного микроконтроллера STM32, официальный файл обновления HHKB Hybrid (`HHKB800_FW_A048.hfb` размером 282 672 байта) представляет собой **комбинированный контейнер для двух независимых чипов**:

1. Первые 64 КБ (`0x0004–0x10003`) — прошивка для основного контроллера STM32 (Bank 2).
2. Оставшиеся ~216 КБ — бинарный образ обновления с собственным заголовком для Bluetooth-чипа **Nordic nRF52832** (SoftDevice + BLE-приложение).

### Почему нельзя распространять готовый HFB-релиз DMK для Hybrid

Поскольку вторая секция контейнера содержит заводскую закрытую прошивку Bluetooth от PFU Limited, распространение готового скомпилированного файла `.hfb` для Hybrid напрямую нарушало бы авторские права производителя. Репозиторий DMK содержит исключительно открытый исходный код без проприетарных бинарных блобов.

### Почему не сработал «чистый» образ из CI (Попытка генерации без заводских блобов)

В процессе разработки была предпринята попытка собирать в GitHub Actions полностью независимый чистый образ обновления:

- Секция STM32 заполнялась открытым кодом DMK.
- Секция nRF заполнялась намеренно невалидными данными / пустой заглушкой с заведомо неверной контрольной суммой (CRC16/MD5).

**Расчёт был на следующее поведение:** загрузчик Nordic nRF52832 отбракует повреждённый образ Bluetooth и сохранит свою текущую заводскую прошивку, а STM32 успешно обновится на DMK.

**Реальный результат аппаратных тестов на физической плате Hybrid:**

1. Загрузчик nRF действительно корректно валидирует образ в промежуточной области (staging area), фиксирует несовпадение MD5/CRC и **безопасно сохраняет заводскую BLE-прошивку**, не допуская окирпичивания радиомодуля.
2. Однако процедура обновления управляется бутлодером **STM32 Bank 1**, который во время `commandE3` запрашивает у Nordic статус приёма прошивки по шине SPI.
3. Получив от Nordic сигнал об ошибке/отказе, **STM32 Bank 1 бракует всю процедуру обновления целиком**: он стирает временные данные, не выставляет в EEPROM флаг успешной валидации (`0x08080360 = 1`) и отказывается передавать управление коду DMK в Bank 2.

Таким образом, создать «чистый» HFB, который штатный загрузчик согласился бы запустить без одновременного успешного обновления nRF, стандартным путем невозможно.

### Единственное проверенное и рабочее решение — локальный патчинг

Чтобы обойти аппаратную блокировку Bank 1 и одновременно не распространять закрытый код nRF, используются утилиты локального патчинга (автономная страница [hhkb.html](../../../../tools/hhkb/hhkb.html) или скрипт `tools/hhkb/patch_hybrid_hfb.py`):

1. Пользователь самостоятельно скачивает оригинальный файл обновления со [страницы загрузок PFU](https://happyhackingkb.com/download/) (`HHKB800_FW_A048.hfb` для ANSI или `HHKB820_FW_JP_A249.hfb` для JIS).
2. Патчер берёт открытый бинарник DMK (`dmk_hhkb_stm32l072.bin`), заменяет в оригинальном файле **только первые 64 КБ секции STM32**, оставляет нетронутой валидную заводскую секцию nRF и пересчитывает внешние контрольные суммы контейнера.
3. Полученный локальный файл содержит валидный для загрузчика nRF образ, поэтому Bank 1 успешно завершает прошивку обоих контроллеров и активирует DMK.

### Hybrid: локальный HTML-патчинг и прошивка в браузере

Скачайте [hhkb.html](../../../../tools/hhkb/hhkb.html) и откройте в Chrome или Edge. Патчинг работает офлайн. Вкладка Flash keyboard использует WebHID и запрашивает доступ к устройству. Некоторым браузерам нужен запуск страницы через localhost. После перезапуска в recovery выберите PFU-интерфейс повторно. SW6 должен быть OFF. Ошибка передачи останавливает обновление и появляется в логе.

Для **Hybrid и Hybrid Type-S** этот HTML-файл позволяет подготовить обновление без установки Python:

1. Откройте вкладку **Hybrid patching**. Перейдите по ссылке [PFU для ANSI](https://happyhackingkb.com/download/) или [PFU для JIS](https://happyhackingkb.com/jp/download/) и самостоятельно скачайте `HHKB800_FW_A048.hfb` (ANSI) либо `HHKB820_FW_JP_A249.hfb` (JIS).
2. Выберите этот файл в **Original PFU update (.hfb)**, а соответствующий DMK `.bin` из релиза или сборки — в **DMK STM32 firmware (.bin)**. Проверьте показанные модель и версию обоих файлов, затем нажмите **Patch and download**. Страница заменит только образ STM32, сохранит оригинальную прошивку Nordic и скачает готовый `.hfb`. Обработка локальная: файлы прошивок никуда не загружаются.
3. Для записи результата откройте **Flash keyboard**, выберите скачанный `.hfb` и нажмите **Connect and flash** либо используйте описанные в [инструкции по установке](install.md) утилиты [HHKB Keymap Tool](https://happyhackingkb.com/download/) / DMK flasher.

Вкладка **Hybrid patching** принимает только официальные HFB Hybrid ANSI A0.48 или JIS A2.49: проверяются оба CRC, версия и SHA-256. Нужен свежий DMK `.bin` со встроенными данными модели и версии. После загрузки каждого файла показываются модель и версия; несовпадение моделей или раскладок блокирует патчинг. Старые DMK-бинарники без этих данных нужно пересобрать. Для Hybrid и Hybrid Type-S используется общий образ соответствующей раскладки; ANSI и JIS различаются.

### Теоретическая альтернатива: многостадийный сценарий без патчинга (Multi-stage Workaround)

Теоретически можно было бы обойтись без локального патчинга файлов PFU и поставлять полностью чистые образы DMK, если обойти проверку статуса nRF в самом Bank 1. Для этого рассматривается сложный 4-ступенчатый сценарий:

1. **Шаг 1 (Временная прошивка):** Мы создаём чистый образ с фиктивной/пустой прошивкой Bluetooth, но с валидными для nRF заголовками и контрольными суммами. Загрузчик nRF принимает её (Bluetooth перестаёт работать, но прошивка считается успешной). Загрузившись в Bank 2, временный код STM32 модифицирует Flash-память Bank 1, пропатчивая проверку статуса nRF (делая её безусловно успешной).
2. **Шаг 2 (Восстановление Bluetooth):** Пользователь прошивает официальный файл обновления PFU через штатный апдейтер. Он восстанавливает оригинальную заводскую прошивку на чипе Nordic nRF52832.
3. **Шаг 3 (Установка чистого DMK):** Пользователь прошивает чистый релиз DMK с намеренно невалидной секцией nRF. Чип nRF отвергает этот образ и сохраняет заводскую BLE-прошивку (из Шага 2). А пропатченный на Шаге 1 бутлодер Bank 1 игнорирует отказ nRF, считает Bank 2 валидным и успешно запускает DMK.
4. **Шаг 4 (Откат и очистка):** При необходимости возврата к стоку переключатель SW6 переводит клавиатуру в Recovery, а прошивка DMK восстанавливает оригинальный код проверки в Bank 1.

> [!CAUTION]
> **Критический риск окирпичивания клавиатуры:**
> Этот вариант несёт в себе колоссальный риск:
>
> - Заводской Bank 1 является **единственным аппаратно защищённым путем восстановления (recovery path) через USB**.
> - Если в процессе модификации Bank 1 (Шаг 1) произойдёт сбой питания, ошибка адресации или зависание, клавиатура полностью потеряет возможность определяться по USB и прошиваться стандартными утилитами. Восстановить её можно будет только через программатор SWD с полной разборкой корпуса.
>
> Из-за неоправданного риска для конечного пользователя локальный патчинг остаётся значительно более простым, надёжным и безопасным решением.

## Патчинг прошивки Hybrid (Python CLI)

Нужен **именно** заводской файл `HHKB800_FW_A048.hfb`. Получите его отдельно в [официальном центре загрузки HHKB](https://happyhackingkb.com/download/) или используйте сохранённую копию. Ожидаемый SHA-256: `635b995eb5a15aa50c2cedc60da7d8998fcca8285a09d41d984c07fffcaf9d43`. Оригинал и полученные контейнеры храните в каталоге `keyboards/hhkb/local/`, исключённом из Git.

Из корня репозитория:

```bash
mkdir -p keyboards/hhkb/local
# Сначала положите исходный HHKB800_FW_A048.hfb в keyboards/hhkb/local/.
./build_all.sh -b hhkb -d HHKB_HYBRID -c
python3 tools/hhkb/patch_hybrid_hfb.py \
  build/hhkb-script/dmk_hhkb_stm32l072.bin \
  keyboards/hhkb/local/HHKB800_FW_A048.hfb \
  keyboards/hhkb/local/dmk_hybrid.hfb
```

Для **Hybrid JIS** добавьте `HHKB_JIS` к флагам сборки и передайте патчеру `--layout jis` вместе с оригинальным `HHKB820_FW_JP_A249.hfb`. Патчер сохраняет модель `AHJX01` и устанавливает версию `A2.50`. Для ANSI используется `AHUX01 / A0.50`.

[patch_hybrid_hfb.py](../../../../tools/hhkb/patch_hybrid_hfb.py) проверяет хеш оригинала, размер и таблицу векторов Bank 2, заменяет только 64 КиБ приложения STM32, дополняет их `FF` и пересчитывает две CRC. Заводской образ nRF сохраняется; версия HFB устанавливается в A0.50 (ANSI) или A2.50 (JIS). Скрипт не перезаписывает существующий выходной файл: для новой сборки укажите новое имя. **Работоспособность полученного таким образом образа проверена и подтверждена на реальном оборудовании HHKB Hybrid.**

Rapid Trigger и АЦП 16 МГц доступны во всех сборках HHKB. Rapid Trigger и оверсемплинг настраиваются в VIA во время работы.
